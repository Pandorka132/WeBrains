# IntelliJ Platform comparison audit

**Audit date:** 2026-10-18

WebBrains is a static React/TypeScript application. This audit distinguishes behavior from visual resemblance: there is no JVM runtime, Swing/AWT, arbitrary IntelliJ plugin JAR loading, or local OS process execution.

## Changes made in this pass

- The bottom tool window has all four rounded corners and sits inside the central workbench area, aligned to the editor's left/right insets (tool-stripe width plus one workbench gap) with a 6 px bottom margin. The stripes no longer overlap its rounded corners or content. Its surface is `#191a1c`; the workbench background is `#26282c`.
- Shared CSS variables now drive stripe widths, workbench gaps, editor insets, and bottom-panel margins. At narrow widths the side docks overlay the editor instead of shrinking the editor and right dock into an unusable sliver; an unused right dock stays available through its stripe drop target.
- Repeated trailing CSS overrides were folded into the main workbench layout rules, duplicate dock styling and 29 obsolete legacy rules were removed, and `App.css` was formatted into readable rule blocks. The stylesheet regression suite checks selector/declaration duplication within each cascade scope.
- Editor line highlighting now follows the 21 px line height used by the gutter and syntax layer. Caret status updates while moving the caret and splits text on actual LF separators.
- Editor input now updates the minimal changed document range rather than replacing the whole document on each keystroke. `DocumentModel` normalizes CRLF/CR to LF, and `EditorModel` tracks caret/selection offsets through edits.
- Editor/document resources are disposed when tabs close, projects change, or the IDE unmounts.
- Save queues and save status are keyed by project plus file path, avoiding collisions between similarly named files from different projects. Local edits are coalesced before BrowserFS queues IndexedDB writes; Google Drive keeps a longer debounce. The in-app project-navigation controls flush pending writes and wait for them to finish, and navigation stays in the editor if a write fails.
- VFS path normalization resolves `.`/`..`, rejects traversal above the project root, validates entry names, and avoids root-prefix collisions. Local metadata and persisted Drive tokens are validated; file-open/create failures are surfaced instead of becoming unhandled rejections. Common binary extensions are refused by the text editor so PNG/ZIP/PDF-like assets are not accidentally decoded and overwritten as UTF-8; this is a conservative extension heuristic, not full MIME/content detection.
- Keyboard shortcuts now match IntelliJ conventions where supported: `Shift` twice and `Ctrl/Cmd+Shift+N` open the current file-name search (not full Search Everywhere), Find Action uses `Ctrl/Cmd+Shift+A`, New File uses `Alt+Insert`, Project uses `Alt+1`, and Run tool window uses `Alt+4`. `Ctrl/Cmd+S` flushes pending saves for all open writable tabs. Unsupported parameter info and text search report that they are not implemented.
- Internal links, the favicon, and JetBrains SVG assets now use Vite's base URL. Project tree disclosure, folder/file icons, New action, search, and file-type icons use assets copied from the JetBrains IntelliJ Community source under Apache 2.0, with attribution in `public/icons/intellij/NOTICE.txt`. The remaining in-component `svg` drawings in `IdePage.tsx` were removed.
- The Project tree has a collapsible project root with nested rows indented relative to the root icon. Nested directories have real disclosure buttons using the upstream chevron and CSS rotation. New, Expand All, and Collapse All use JetBrains SVG assets; creation targets the selected directory or the project root. Right-click menus are implemented for root, directory, and file nodes, with only currently supported actions exposed.
- Tool-window icons can be dragged to another dock group and dropped on another icon to reorder before/after it. A live placeholder previews the insertion point and the surrounding icons reflow while dragging; the native drag source stays mounted until a preview target is entered. Their order persists separately from dock assignment. Left/right vertical stripes each have an upper and lower group separated by a short divider; the divider itself and the area directly below it both target the lower side dock. The bottom panel's tool-window groups are represented at the foot of the vertical stripes: the left stripe hosts the bottom group and the right stripe hosts the bottom-right group. The divider separates the upper and lower side-panel icon groups, and the bottom-panel icon groups remain beneath a flexible spacer. The six panel instances now share one panel-frame/header renderer. Panel gaps, horizontal alignment, and corner radii share workbench variables instead of separate inline offsets. Bottom tool windows are laid out left/right as separate rounded panes when both bottom groups are open. Dropping a header onto a single side panel chooses upper/lower placement based on the half of the panel under the pointer, matching the upstream `ToolWindowDropArea` split rule. Empty groups do not render a fake “Drop a tool window here” panel; their stripe remains a valid drop target.
- GitHub Pages builds use a repository-aware base and hash routing, with pure routing regression tests; the deployment workflow runs lint and all test suites before deployment.

## Follow-up audit: tree and dock interactions

- Fixed the root-level indentation bug by making the project root an actual disclosure row and indenting its children as descendants, rather than siblings aligned to the root label.
- Added the upstream `expui/general/expandAll.svg` and `collapseAll.svg` assets (Apache 2.0, credited in `frontend/public/icons/intellij/NOTICE.txt`) and wired them to tree-wide expansion controls.
- Added right-click menus for project root, directory, and file rows. These currently expose New File/New Directory where applicable, Open for files, and Expand All/Collapse All. Rename, Delete, Copy Path, VCS, and other actions are intentionally not advertised until their underlying behavior is implemented and verified.
- The bottom dock row now uses the tool-stripe inset rather than adding the full left/right side-panel widths, which had pushed the bottom row too far toward the center.
- Drag-over now highlights actual side/bottom dock panes and stripe groups with a blue target outline/fill; drag-leave clears the highlight. This is an initial drop-target affordance, not yet a pixel-perfect reproduction of IntelliJ's split insertion line/blue preview region.
- Run/Debug toolbar actions and tool-window buttons reference the existing IntelliJ source SVG assets (`run-action.svg`, `debug-action.svg`, `run.svg`, `debug.svg`) rather than Unicode glyphs. The runtime actions remain placeholders because no browser execution/debug runtime is connected.

## Subsystem comparison

### Workbench and tool windows

The official SDK describes tool windows and their anchors; current source checks included [`ToolWindowPaneNewButtonManager`](https://github.com/JetBrains/intellij-community/blob/master/platform/platform-impl/src/com/intellij/toolWindow/ToolWindowPaneNewButtonManager.kt), [`ToolWindowPane`](https://github.com/JetBrains/intellij-community/blob/master/platform/platform-impl/src/com/intellij/toolWindow/ToolWindowPane.kt), [`ToolWindowDragHelper`](https://github.com/JetBrains/intellij-community/blob/master/platform/platform-impl/src/com/intellij/toolWindow/ToolWindowDragHelper.kt), [`ToolWindowDropArea`](https://github.com/JetBrains/intellij-community/blob/master/platform/platform-impl/src/com/intellij/toolWindow/ToolWindowDropArea.kt), [`ToolWindowLeftToolbar`](https://github.com/JetBrains/intellij-community/blob/master/platform/platform-impl/src/com/intellij/toolWindow/ToolWindowLeftToolbar.kt), [`ToolWindowRightToolbar`](https://github.com/JetBrains/intellij-community/blob/master/platform/platform-impl/src/com/intellij/toolWindow/ToolWindowRightToolbar.kt), and [`ToolWindowHeader`](https://github.com/JetBrains/intellij-community/blob/master/platform/platform-impl/src/com/intellij/toolWindow/ToolWindowHeader.kt). These confirm that the new UI uses left/right stripes, that bottom-anchored tools are represented in the left toolbar when the horizontal stripe extension is absent, and that drag targets split an area into halves. See [Tool Windows](https://plugins.jetbrains.com/docs/intellij/tool-windows.html) and [UI overview](https://plugins.jetbrains.com/docs/intellij/ui-overview.html).

WebBrains models upper/lower side-panel groups on both the left and right stripes; both stay in the upper section, with the divider between those two groups. Bottom-panel tools are a separate group at the very bottom of each vertical stripe (left stripe for the bottom group, right stripe for the bottom-right group); there is no horizontal bottom icon stripe. Tool panels still share the common panel renderer, with draggable icons/headers, resize handles, and persisted tool-to-dock assignments. Layout v3 assignments that incorrectly placed Problems/Terminal/Run/Debug in lower side-panel groups migrate into their corresponding bottom-panel groups. The empty right side intentionally remains a drop target. Tool-window factories, lazy content creation, content-manager tabs, floating/detached windows, full focus behavior, and all IntelliJ stripe policies are not implemented.

### Documents, editor, and language services

The platform now has versioned range edits, synchronous document-change events, LF normalization, and caret/selection offset mapping. The visible editor is still a textarea with a syntax-colored overlay and heuristic tokenization. There is no PSI tree, parser runtime, incremental PSI invalidation, undo/redo manager, guarded blocks, injected language, multi-caret, folding, inlays, completion lookup, inspections daemon, or refactoring engine. Syntax coloring is not semantic analysis.

### VFS and persistence

Memory, BrowserFS/IndexedDB, and Google Drive adapters share a virtual filesystem contract. Absolute paths outside a provider's root are rejected, relative paths normalize `.` / `..`, and local project IDs are validated before they become paths. Browser policy prevents transparent access to arbitrary disk paths, mounts, symlinks, and native file watchers. Drive project loading recursively lists directories before displaying the tree; this can be slow for very large projects, so lazy loading, cancellation, and bounded concurrency should precede indexing large workspaces.

**Persistence caveat:** the local provider uses BrowserFS `AsyncMirror`. Its in-memory write completes synchronously while the IndexedDB write is queued asynchronously; the current provider API does not receive a durable-commit acknowledgement from that queue. Therefore the UI's `Saved` state means the write was accepted by the active filesystem adapter, not that an IndexedDB transaction has definitely committed. A durable local-save acknowledgement layer is still required before making a stronger crash-durability guarantee. Drive access tokens currently live in `localStorage`, which is accessible to same-origin JavaScript and increases the impact of XSS; keep the `drive.file` scope narrow and revisit persistence as part of the security model.

### Services, plugins, lifetimes, and threading

WebBrains implements explicit disposable scopes, typed message topics, in-memory service containers, extension/action registries, project/module objects, and a metadata-only plugin catalog. IntelliJ services have application/project/module scopes, lazy initialization, descriptor-driven extension registration, and plugin-unload semantics. WebBrains does not instantiate arbitrary descriptor class names, load JARs, execute Java/Kotlin plugin code, or guarantee upstream service lookup/override semantics. See [Services](https://plugins.jetbrains.com/docs/intellij/plugin-services.html) and [Disposer / Disposable](https://plugins.jetbrains.com/docs/intellij/disposers.html).

IntelliJ uses an EDT/background-thread model and read/write access rules for PSI, VFS, and project data. A browser needs different concurrency contracts: expensive parsing/indexing should use Web Workers or cancellable asynchronous work, not a mechanical copy of Java read/write locks. See the [Threading Model](https://plugins.jetbrains.com/docs/intellij/threading-model.html). A static site cannot run arbitrary local processes or JVM bytecode; Terminal/Run/Debug remain placeholders unless implemented with explicit browser-native or separately designed remote execution.

## Deep editor ownership audit: IntelliJ Platform vs. Python CE

**Audited:** 2026-10-19. The concrete plugin target is Python Community Edition `263.7031.23` (`PythonCore`), from the locally available plugin artifact. The findings below are based on its embedded `META-INF/plugin.xml` module descriptors and class inventory, cross-checked against the IntelliJ Platform Plugin SDK. This is a responsibility map, not a claim that WebBrains already implements these APIs.

### The ownership rule

The editor is a platform engine with language-plugin contributions. The platform owns generic editing mechanics and the extension-point infrastructure; Python CE registers Python-specific implementations into that infrastructure. A feature can be split across both layers: the platform owns the interaction lifecycle and rendering, while Python CE decides what the interaction means for Python.

| Capability | Platform/editor responsibility | Python CE responsibility | WebBrains status |
|---|---|---|---|
| Text input, caret, selection, document changes | Document/editor model, caret and selection, keyboard dispatch, edit transactions, scrolling, rendering and lifecycle | Python-specific handlers may intercept/augment certain actions | Basic textarea + overlay and a minimal document/caret model only; no IntelliJ-equivalent editor engine |
| Enter and indentation | Runs the Enter-handler pipeline, applies editor/code-style settings, inserts newline/indent, handles selection and caret consistently | `PythonEnterHandler` and `PyEnterAtIndentHandler` provide Python-aware behavior; `PyLanguageCodeStyleSettingsProvider`, code-style settings and Python formatting support influence indentation | `CodeEditor.tsx` now dispatches through the platform `EditorKeyHandlerRegistry`. Python CE contributes a transitional regex-based Enter handler; it is not the original Python CE handler and is not behaviorally equivalent |
| Tab / indent / unindent | Generic editor action, selection handling, tab-vs-spaces settings, keymap and code-style integration | Python settings can define language-specific defaults and smart-key behavior | `CodeEditor.tsx` now delegates to platform commands. Basic selected-line indent and Shift+Tab unindent exist, using the language service's `tabSize`; broader code-style settings and IntelliJ keymap semantics are still absent |
| Syntax coloring | Token-highlighter interfaces, text-attribute keys, color schemes and drawing | Python lexer/highlighter and token categories | Original Python CE lexer is compiled to WASM for a narrow tokenization slice. The visible renderer is custom and has a regex fallback; theme/attribute-key parity is absent |
| Syntax errors | Parser framework builds error nodes; the analysis daemon converts parser errors to editor highlights | Python grammar/parser and parser definition decide which tokens are invalid and where errors belong | The original parser now produces real error ranges in a JVM probe with the real IntelliJ mock application and Python services; its Wasm build is blocked by a GraalVM analysis failure. The browser editor still shows lexical errors only |
| Semantic highlighting and errors | PSI traversal, highlighting passes, annotation scheduling, severity/range rendering, cancellation and stale-result invalidation | Python annotators such as `PySyntaxAnnotator`, `PyDefinitionsHighlightingAnnotator`, `PyLocalVariableHighlightingAnnotator`, `PyBuiltinHighlightingAnnotator` and others analyze Python PSI | Only a generic diagnostics data shape and underline renderer exist; Python's original annotators are not running |
| Inspections and quick fixes | Inspection/daemon framework, settings, highlighting presentation, quick-fix UI and document-change integration | Python CE registers many `localInspection` implementations and corresponding fixes; examples cover unused symbols, type hints, invalid calls, control flow, style, and many other checks | Not implemented. A generic `diagnose()` callback alone does not provide PSI, inspection visitors, settings, fixes or daemon semantics |
| Completion / automatic suggestions | Completion action and invocation, auto-popup triggers, contributor collection, lookup popup, filtering/sorting, insertion handlers, cancellation and editor integration | Python completion contributors provide context-sensitive candidates (keywords, parameters, class/super methods, dict keys, f-strings, type-related forms, docstrings, etc.); Python confidence/typed handlers influence when completion appears | No completion engine or lookup popup. There are no Python completion contributors connected to the editor. The current language service's optional `diagnose` method does not implement completion |
| Documentation, parameter info, references and navigation | Popup/hint lifecycle, editor context, reference resolution and navigation framework | Python documentation provider, reference contributors, type/resolve services and completion integrations provide Python-specific information | Not implemented; these features depend on parser/PSI, references, project model, indexes and often interpreter/SDK/stubs |
| Quotes, brackets, typing and selection | Generic typing pipeline, pair handling, backspace/selection extension hooks | Python CE registers `PythonQuoteHandler`, `PyBraceMatcher`, `PythonSpaceHandler`, `PyKeywordTypedHandler`, triple-quote backspace handling, Enter-between-braces behavior, and Python-specific word/statement selection handlers | Mostly native textarea behavior. No matching extension pipeline for auto-pairs, quote behavior, structural selection, smart backspace or join-lines |
| Formatting and smart Enter | Formatter framework, formatting model invocation, code-style configuration and editor actions | Python formatting model, pre/post-format processors, language code-style settings and `PySmartEnterProcessor` | Not implemented; Enter's simple indentation heuristic is not a formatter or Smart Enter implementation |
| Folding and editor structure | Folding model, collapsed-region state, gutter/scroll rendering and fold actions | Python folding builder determines foldable language constructs | Line-number gutter exists, but code folding is absent |
| Live templates and postfix completion | Template expansion engine, variable evaluation, popup/action and insertion mechanics | Python CE contributes Python template contexts, macros, preprocessors and postfix templates | Not implemented |
| Project-aware insight | Project/module model, VFS, indexes, dumb-mode policy, background tasks and service lifetimes | Python plugin contributes PSI references, type evaluation, import resolution, inspections, SDK-aware behavior and integration with Python tooling | Project tree and VFS exist in a limited form, but there is no Python PSI/index/resolve/type engine or configured interpreter environment |

### What the real Python CE descriptor confirms

The descriptor does not describe a single “Python lexer plugin.” It registers a broad family of implementations against platform extension points. Examples from the actual `263.7031.23` artifact:

- **Editor actions:** `PythonEnterHandler`, `PyEnterAtIndentHandler` (ordered first), `PythonQuoteHandler`, `PyBraceMatcher`, `PythonSpaceHandler`, `PyKeywordTypedHandler`, triple-quote backspace delegate, statement mover, join-lines handler, and Python word/statement selection handlers.
- **Language structure and highlighting:** `PythonParserDefinition`, `PythonEditorHighlighter`, a syntax-highlighter factory, Python parser/lexer classes, and multiple Python annotators.
- **Completion:** numerous `completion.contributor` declarations, including `PyKeywordCompletionContributor`, `PyParameterCompletionContributor`, `PyClassNameCompletionContributor`, `PyDictKeyNamesCompletionContributor`, f-string and docstring contributors, plus `PyCompletionConfidence`.
- **Diagnostics:** parser error elements, Python annotators and a large set of `localInspection` declarations. These are distinct mechanisms; one lexer cannot replace them.
- **Other code insight:** Python documentation and reference contributors, formatting model and format processors, folding builder, Smart Enter processor, live-template contributions, import optimization, and line-marker providers.

The package's embedded module descriptors also include auxiliary languages and integrations (for example Python stubs, doctests, requirements, regular expressions, LSP and Ruff-related modules). Aggregate descriptor counts therefore must not be interpreted as a count of Python-only features or as proof that every optional integration is available in every product configuration.

### Consequences for WebBrains architecture

1. **Remove Python semantics from `CodeEditor`.** The editor should dispatch platform editing commands and consume registered language/editor extensions. It should not know Python keywords, parse Python block headers, or implement a second Python-specific rule set in React.
2. **Do not treat the key-handler registry as IntelliJ compatibility by itself.** The new `EditorKeyHandlerRegistry` is a first platform seam with ordering, disposable registrations, validated edit ranges, selection-aware edits and fallback Enter/Tab commands. It still lacks IntelliJ command/write transaction semantics, the full smart-key delegate pipeline, complete code-style settings and keymap behavior. Python's current Enter contribution remains a temporary regex adapter until the original handler's dependencies and contract are runnable.
3. **Model completion as its own subsystem.** At minimum this requires invocation/autopopup triggers, a versioned document/caret context, cancellable contributor requests, result merging and ordering, lookup UI, and insertion edits. Python CE contributors then supply candidates. Real Python semantic completion additionally depends on PSI, references/resolution, project indexes, type evaluation and often SDK/stub information; adding a popup alone would be cosmetic, not Python completion.
4. **Build the analysis pipeline in layers.** Original lexer → original parser and `ParserDefinition` → PSI/AST construction and invalidation → parser error ranges → platform diagnostic scheduling/rendering. Then add Python annotators and inspections. Keep lexical, grammar, semantic and external-tool diagnostics distinct so their ranges/severities and cancellation behavior remain traceable.
5. **Translate registrations, not just names.** The current `BrowserPluginModule`/`EditorLanguageServiceRegistry` is not a runtime for arbitrary `plugin.xml` implementations. A descriptor entry must either map to a compatible browser implementation with conformance tests, be explicitly marked unsupported, or remain deferred. Silently pretending an extension is supported would misrepresent compatibility.
6. **Preserve the browser-only constraint honestly.** The original plugin's Java/Kotlin classes cannot execute just because their JARs are present. The existing WASM lexer proves one selected class slice can run after compilation; it does not establish that the parser, PSI, completion, inspections, or the whole plugin can run in the browser. Each additional slice needs its actual dependency closure, startup services, reflection/runtime requirements and tests assessed.

### Recommended implementation order

1. Inventory the exact `PythonCore` extension registrations and their declaring modules; record dependencies and which are Python-specific versus optional integrations.
2. Make the editor consume a platform command/handler API rather than hard-coding Enter/Tab behavior in React. Initially preserve only generic editing behavior and keep the temporary Python heuristic clearly marked as transitional until the original handler can run.
3. Port the verified JVM parser bootstrap to the browser-compatible runtime. The original service implementation and required dialect-token extension point are now identified and used in the JVM probe. Do not introduce a fake `PyElementTypesFacade`, a handwritten Python parser, or a regex syntax checker as a substitute.
4. Establish real error ranges from the parser and validate them against Python CE fixtures before wiring annotators/inspections.
5. Implement the completion lifecycle and lookup UI at the platform layer, then bring over Python CE contributors in dependency-aware slices.
6. Add the remaining smart-key, formatting, folding, documentation, reference, intention and inspection families incrementally, with behavior tests against the chosen IntelliJ build.
